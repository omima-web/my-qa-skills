# Test Plan template (sprint-level) + how to populate it

Used only in the **MCP path**, when creating the sprint Test Plan that doesn't yet exist. Create the Test Plan issue via the **Jira connector** (`createJiraIssue`, issuetype "Test Plan") so the rich description below renders cleanly as markdown; then use the MCP (`addTestsToTestPlan`) to assign tests. Search first — never create a second plan for a sprint that already has one.

## Population rules (auto-fill what's derivable; template the rest)
- **Sprint name + dates** → from the story's Sprint (`customfield_10020` → the sprint's name / start / end).
- **In-Scope stories** → `searchJiraIssuesUsingJql("sprint = <sprintId> AND issuetype = Story", fields: summary, components, labels)` → list keys + titles, grouped by sub-module / component. This is a **snapshot** at creation.
- **Risks** → fold in any linked bugs / dependencies surfaced during ticket-reading (step 6b) if known; else leave the templated line.
- **QA / roles** → the stories' `QA Engineer` field if populated; else leave the placeholder.
- **Out of Scope / Approach / Environment / Entry / Exit / Deliverables** → sensible defaults below; the quality team refines.

**On reuse (plan already exists): do NOT overwrite its description** — respect any manual edits. Optionally note in the report if the sprint now has stories not reflected in the plan's In-Scope snapshot.

## The template (fill the <...> and the story list, keep the rest)
```
# Test Plan — <Sprint Name>

## 1. Purpose
Sprint-level QA plan for <Sprint Name>, covering the stories delivered this sprint. Auto-generated by qa-create-testcase — refine scope and criteria as needed. Scope is a snapshot at creation; confirm against the live sprint board.

## 2. In Scope
Stories/features under test this sprint (snapshot <date>):
- <SHPD-XXXX> — <title>  (<sub-module>)
- <SHPD-XXXX> — <title>  (<sub-module>)
- …

## 3. Out of Scope
- Performance, load, and stress testing (unless a story explicitly requires it)
- Security / penetration testing (separate effort)
- Third-party provider internals (courier, payment, mapping systems) — tested only at the integration boundary
- Modules/features not part of this sprint's stories
- <refine per sprint>

## 4. Test Approach
- Layers: Backend (API), UI (Dashboard/Store), cross-seam E2E where a story spans both surfaces, mobile sanity where Dashboard is impacted
- Execution: manual via Xray; automatable cases flagged for the automation backlog
- Design: one happy path per AC + earned negatives/boundaries + risk-based edge cases

## 5. Environment & Data
- Environment: Stage
- Test data: per-story preconditions (see individual test cases)

## 6. Entry Criteria
- Stories meet Definition of Ready (ACs testable, design attached for FE, SP set)
- Build deployed to Stage
- Test cases written and reviewed (qa-create-testcase / qa-review-testcase)

## 7. Exit Criteria
- All planned test cases executed
- No open Blocker/Critical (Sev-1/Sev-2) defects
- Pass rate ≥ <team threshold, e.g. 95%>; remaining failures triaged and documented
- Known issues logged with severity and owner

## 8. Test Deliverables
- This Test Plan, the per-story Test Sets, the test cases, and Test Execution results

## 9. Risks & Assumptions
- <linked bugs / dependencies that could block execution, from ticket-reading — e.g. "open bug SHPD-Y affects AC-Z">
- Assumes design docs / API contracts are finalized before execution
- <refine per sprint>

## 10. Schedule & Roles
- Sprint: <start> → <end>
- QA: <QA engineers on the sprint's stories, or TBD>
- Reviewed by: <lead / TBD>

_Generated <date> by qa-create-testcase — scope is a snapshot; confirm against the live sprint board._
```
